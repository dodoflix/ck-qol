# Core Keeper QoL

Client-side quality-of-life tweaks for Core Keeper, bundled as one PugMod mod so
they share a single config file and a single install.

Targets Core Keeper **1.2.1.5** (Unity 6000.0.59f2).

## Install

```sh
./install.sh
```

Close the game first — mods are compiled at startup, so a running client will not
pick up changes. Then launch and check the log:

```sh
tail -f "$HOME/.local/share/Steam/steamapps/compatdata/1621690/pfx/drive_c/users/steamuser/AppData/LocalLow/Pugstorm/Core Keeper/Player.log" | grep CkQol
```

`install.sh` deploys to `CoreKeeper_Data/StreamingAssets/Mods/CkQol/` inside the
game install. Set `CK_GAME_DIR` if your install lives elsewhere.

> Steam can wipe `StreamingAssets/` on game updates and on Verify Integrity.
> Re-run `install.sh` if the mod stops loading after either.

## How it works

PugMod ships **C# source**, not a compiled DLL — the game carries Roslyn
(`mcs.dll`, `Microsoft.CodeAnalysis.CSharp.dll`) and compiles mods in-process at
startup. So there is no build step here, and compile errors show up in the game
log rather than at deploy time.

`ModManifest.json` is generated by `install.sh` from whatever is in `src/`.
This is deliberate: PugMod silently ignores any `.cs` file not listed in the
manifest, which is indistinguishable from a feature that just does not work.

## Adding a feature

Create a class in `src/Features/` extending `QolFeatureBase`:

```csharp
namespace CkQol.Features
{
    public class MyTweak : QolFeatureBase
    {
        public override string Name => "MyTweak";
        public override string Description => "What it does, shown by the config toggle.";

        public override void OnWorldCreated()
        {
            Log("world is up");
        }
    }
}
```

Then register it in `CkQolMod.BuildFeatures`:

```csharp
yield return new Features.MyTweak();
```

Every feature gets an on/off toggle under `[Features]` in the mod's config
automatically, keyed on `Name` — renaming `Name` orphans the user's existing
setting.

Features are isolated: one that throws in any lifecycle callback is logged and
disabled, and the rest keep running.

## API notes

Reachable through `PugMod.API`:

| | |
|---|---|
| `API.Client.World` | client DOTS world |
| `API.Client.LocalPlayer` | local player `GameObject` |
| `API.Client.OnWorldCreated` / `OnWorldDestroyed` | world lifecycle |
| `API.Client.OnObjectSpawnedOnClient` / `OnObjectDespawnedOnClient` | entity spawn hooks |
| `API.Client.GetEntityQuery(...)` | ECS queries |
| `API.Client.GetGraphicalGameObject(entity)` / `GetEntity(go)` | entity ↔ GameObject |
| `API.Client.AddMainThreadSystem(...)` / `AddScheduledSystem(...)` | custom ECS systems |
| `API.Config.Register<T>(mod, section, description, key, default)` | config, returns `IConfigEntry<T>` with `.Value` |
| `API.ModLoader.ApplyHarmonyPatches(modId)` | Harmony (manifest sets `disableHarmonyPatching: false`) |
| `API.Reflection` | reaching private game internals |

Game code worth knowing about: `Manager.main`, `Manager.ui`, `Manager.saves`,
`Manager.worldGen`, `Manager.ecs`. Most gameplay lives in `Pug.Other.dll`;
worldgen in `WorldGen.dll` / `PugWorldGen.*`; ECS components in
`Pug.ECS.Components.dll`. Decompile with `ilspycmd` against
`CoreKeeper_Data/Managed/`.

## Scope

Client-side only. `requiredOn: 1` (Client) — no server install needed, and other
players do not need the mod.

Anything that changes world state, spawns entities authoritatively, or drives
world generation belongs on the server and is out of scope here.

## Status

`LoadProbe` is a placeholder that only logs lifecycle events, there to confirm the
