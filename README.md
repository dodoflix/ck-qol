# Core Keeper QoL

Client-side quality-of-life tweaks for Core Keeper, bundled as one PugMod mod so
they share a single config file and a single install.

Targets Core Keeper **1.2.1.5** (Unity 6000.0.59f2).

## Install

```sh
./check.sh     # compile against the game's assemblies first
./install.sh
```

Close the game first — mods are compiled at startup, so a running client will not
pick up changes. Then launch and check the log:

```sh
tail -f "$HOME/.local/share/Steam/steamapps/compatdata/1621690/pfx/drive_c/users/steamuser/AppData/LocalLow/Pugstorm/Core Keeper/Player.log" | grep CkQol
```

`install.sh` deploys to `CoreKeeper_Data/StreamingAssets/Mods/CkQol/` inside the
game install. Set `CK_GAME_DIR` if your install lives elsewhere.

> Steam can wipe `StreamingAssets/` on game updates and on Verify Integrity.
> Re-run `install.sh` if the mod stops loading after either.

## How it works

PugMod ships **C# source**, not a compiled DLL — the game carries Roslyn
(`mcs.dll`, `Microsoft.CodeAnalysis.CSharp.dll`) and compiles mods in-process at
startup. So there is no build step here, and compile errors show up in the game
log rather than at deploy time.

`ModManifest.json` is generated by `install.sh` from whatever is in `src/`.
This is deliberate: PugMod silently ignores any `.cs` file not listed in the
manifest, which is indistinguishable from a feature that just does not work.

`check.sh` compiles the source against `CoreKeeper_Data/Managed/` so mistakes
surface in a couple of seconds instead of as a line in `Player.log` after a full
game launch. Run it before every install.

## The config menu

**Main Menu / Pause → Options → Core Keeper QoL.** No hotkey, no separate window.

Each feature gets a page with an Enabled toggle and its settings. Changes apply
immediately and are saved — there is no apply button and no restart.

The menu is built from Core Keeper's own option rows rather than reimplemented.
The game's menus are **SpriteRenderer-based world-space UI** driven by
`RadicalMenu`, not uGUI, so a parallel Canvas UI can never quite match: it fights
canvas scaling, sort order, and the game's custom cursor, and a pixel font
renders wrong at any fractional scale. Cloning the real rows sidesteps all of
that and inherits the game's fonts, sounds, controller navigation and pause
behaviour for free.

`GameMenu` clones a donor row, strips its script, and swaps in ours while keeping
every serialized reference. Donors are picked by type-name shape (something
"Toggle"-ish, something "Slider"-ish) rather than by a specific game class, so a
renamed or reordered option does not break it. If no donor is found the mod logs
and carries on without the menu instead of failing to load.

## Adding a feature

Create a class in `src/Features/` extending `QolFeatureBase`:

```csharp
public class MyTweak : QolFeatureBase
{
    public override string Name => "MyTweak";
    public override string Description => "What it does, shown at the top of its tab.";

    private readonly FloatSetting _strength =
        new FloatSetting("Strength", "Strength", 1f, 0f, 5f, "Tooltip text.");

    public override IEnumerable<ModSetting> GetSettings()
    {
        yield return _strength;
    }

    public override void Update()
    {
        // Read .Value every time - that is what makes menu edits apply live.
        DoSomething(_strength.Value);
    }
}
```

Register it in `CkQolMod.BuildFeatures`:

```csharp
yield return new Features.MyTweak();
```

That is all that is needed. The feature gets its own tab, an Enabled toggle, a
config section named after `Name`, and a widget per setting.

Setting types and how they appear:

| type | native row |
|---|---|
| `BoolSetting` | toggle |
| `IntSetting`, `FloatSetting` | slider, using min/max |
| `ChoiceSetting` | slider across the options, stored by name so reordering them later cannot change anyone's setting |
| `StringSetting`, `KeySetting` | no native row yet — config file only |

Two things worth knowing:

- **Read `.Value` at point of use, not at init.** Caching it means menu edits do
  nothing until restart.
- **`Name` is the config key.** Renaming it orphans users' existing settings.

Features are isolated. One that throws in any lifecycle callback is logged,
disabled, and the rest keep running — a broken tweak should not cost you the
other ten or crash the client. Toggling a feature on mid-session runs its `Init`
and, if a world is already loaded, the `OnWorldCreated` it missed.

## API notes

Reachable through `PugMod.API`:

| | |
|---|---|
| `API.Client.World` | client DOTS world |
| `API.Client.LocalPlayer` | local player `GameObject` |
| `API.Client.OnWorldCreated` / `OnWorldDestroyed` | world lifecycle |
| `API.Client.OnObjectSpawnedOnClient` / `OnObjectDespawnedOnClient` | entity spawn hooks |
| `API.Client.GetEntityQuery(...)` | ECS queries |
| `API.Client.GetGraphicalGameObject(entity)` / `GetEntity(go)` | entity ↔ GameObject |
| `API.Client.AddMainThreadSystem(...)` / `AddScheduledSystem(...)` | custom ECS systems |
| `API.Config.Register<T>(mod, section, description, key, default)` | config, returns `IConfigEntry<T>` with `.Value` |
| `API.ModLoader.ApplyHarmonyPatches(modId)` | Harmony (manifest sets `disableHarmonyPatching: false`) |
| `API.Reflection` | reaching private game internals |

Game code worth knowing about: `Manager.main`, `Manager.ui`, `Manager.saves`,
`Manager.worldGen`, `Manager.ecs`. Most gameplay lives in `Pug.Other.dll`;
worldgen in `WorldGen.dll` / `PugWorldGen.*`; ECS components in
`Pug.ECS.Components.dll`. Decompile with `ilspycmd` against
`CoreKeeper_Data/Managed/`.

## Scope

Client-side only. `requiredOn: 1` (Client) — no server install needed, and other
players do not need the mod.

Anything that changes world state, spawns entities authoritatively, or drives
world generation belongs on the server and is out of scope here.

## Status

`LoadProbe` is a placeholder that only logs lifecycle events, there to confirm the
mod loads. Delete it once real features exist.
